# Network Intrusion Detection System (NIDS)

A Suricata-based network intrusion detection system with custom detection
rules, an automated response engine, and a live monitoring dashboard.

Built for: **Task 4 — Network Intrusion Detection System**

## Why Suricata

Suricata was chosen over Snort for this project for one practical reason:
Suricata's `eve.json` output is structured JSON, which plugs directly into
Python without any log-parsing gymnastics. That's what makes the auto-response
script and the dashboard in this repo straightforward to build and demo.
Suricata is also multi-threaded (Snort 2 is single-threaded) and is what
most modern SOCs have standardized on.

## Architecture

```
                    ┌─────────────────────┐
   Network traffic  │                     │
   (live iface or   │      Suricata       │   custom.rules
   replayed pcap) ──▶  (IDS/detect mode)  │◀── (rules/custom.rules)
                    │                     │
                    └──────────┬──────────┘
                               │ writes
                               ▼
                     /var/log/suricata/eve.json
                               │
                 ┌─────────────┴─────────────┐
                 ▼                           ▼
       responder/auto_response.py   dashboard/app.py (Flask)
       (tails eve.json, blocks       (tails eve.json, serves
        repeat offenders via         charts + alert table at
        iptables, logs incidents)    http://127.0.0.1:5000)
```

## 1. Setup

On your lab VM (Ubuntu/Debian):

```bash
cd scripts
sudo bash 01_install_suricata.sh
sudo bash 02_configure_suricata.sh eth0      # replace eth0 with your interface
```

Copy the rules into place and validate the config:

```bash
sudo cp ../rules/custom.rules /etc/suricata/rules/custom.rules
sudo suricata -T -c /etc/suricata/suricata.yaml -i eth0
```

`-T` runs a config test only — it should print `Configuration provided was successfully loaded` with no errors.

## 2. Rules and alerts

`rules/custom.rules` contains 17 rules across six detection categories, using
a dedicated SID range (9000001–9000999) so they never collide with
community rulesets pulled via `suricata-update`:

| Category | Examples | SIDs |
|---|---|---|
| Reconnaissance | SYN/NULL/XMAS/FIN port scans | 9000001–9000004 |
| DoS/floods | ICMP flood, SYN flood, UDP flood | 9000010–9000012 |
| Brute force | SSH, FTP | 9000020–9000021 |
| Web attacks | SQLi, directory traversal, XSS, scanner user-agents | 9000030–9000035 |
| Malware/C2 | DNS tunneling, reverse-shell banners | 9000040–9000041 |
| Policy | Insecure protocol usage (Telnet) | 9000050 |

Threshold-based rules (`threshold:type both, track by_src, count N, seconds S`)
are used wherever a single packet is normal but a burst is not — e.g. one SYN
is a normal connection attempt, 20 SYNs to different ports in 5 seconds is a
port scan. This avoids the classic false-positive trap of alerting on every
individual packet.

## 3. Continuous monitoring

Run Suricata live against your interface:

```bash
sudo suricata -c /etc/suricata/suricata.yaml -i eth0 -D
tail -f /var/log/suricata/eve.json | jq 'select(.event_type=="alert")'
```

For the demo/video walkthrough (no need for a second attacking machine),
generate simulated attack traffic and replay it offline:

```bash
cd scripts
python3 -m venv venv && source venv/bin/activate
pip install -r ../requirements.txt
python3 generate_test_traffic.py --which all

sudo suricata -c /etc/suricata/suricata.yaml -r pcaps/port_scan.pcap -l /var/log/suricata/ -k none
cat /var/log/suricata/eve.json | jq 'select(.event_type=="alert") | .alert.signature'
```

## 4. Response mechanisms

`responder/auto_response.py` tails `eve.json` in real time and applies a
tiered policy:

- **High severity (severity 1)** → blocked immediately via `iptables -I INPUT -s <ip> -j DROP`
- **Repeat offender** (≥3 alerts from the same source within 60s, any severity) → blocked
- **Auto-unblock** after 30 minutes
- Every decision is logged to `incidents.log` with timestamp, source IP, and triggering signature

Run it in dry-run mode first (no root/iptables required — safe for the demo):

```bash
python3 responder/auto_response.py --eve /var/log/suricata/eve.json --dry-run
```

Drop `--dry-run` to have it actually apply `iptables` rules once you're
running on a real lab host.

The reasoning behind not auto-blocking on every single alert: a naive
"block on first alert" policy is itself a DoS vector — an attacker can spoof
source IPs against a noisy low-severity rule to get you to block legitimate
traffic. The severity + repeat-offender threshold is the standard mitigation.

## 5. Dashboard

```bash
cd dashboard
pip install -r ../requirements.txt
python3 app.py --eve ../sample_data/eve.json     # demo mode, no Suricata needed
# or once Suricata is running:
python3 app.py --eve /var/log/suricata/eve.json
```

Open `http://127.0.0.1:5000`. The dashboard shows:

- Total / high / medium / low severity alert counts
- Alert volume over time (line chart)
- Top triggered signatures (bar chart)
- Top source IPs (bar chart)
- Alerts by category (doughnut chart)
- A live-updating table of the most recent 50 alerts, color-coded by severity

It polls `/api/alerts` and `/api/stats` every 5 seconds — no page reload needed.

## Demo script (for the video walkthrough)

1. `suricata -T ...` — show the config validates cleanly
2. `python3 generate_test_traffic.py --which port_scan` — generate one attack pcap
3. Replay it: `suricata -r pcaps/port_scan.pcap -l /var/log/suricata/ -k none`
4. `jq` the resulting `eve.json` to show the alert fired with the right SID
5. Start `dashboard/app.py` pointed at that same `eve.json`, show the alert appear live
6. Start `responder/auto_response.py --dry-run`, replay `ssh_bruteforce.pcap`, show the
   repeat-offender counter trip and the "would block" log line

## Notes / limitations

- Rules are tuned for a lab environment; thresholds (e.g. 20 SYNs/5s for a
  port scan) would need adjusting for a real production network to avoid
  false positives from legitimate bursty traffic.
- The auto-responder's `iptables` block is host-based (blocks on the sensor
  itself). In a real deployment this would typically be swapped for a call
  to a perimeter firewall/router API instead.
- `sample_data/eve.json` is synthetic, generated by `generate_sample_eve.py`,
  and is included purely so the dashboard can be evaluated without needing
  Suricata installed.
